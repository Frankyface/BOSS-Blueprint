## 0. Purpose, consumer, and the one test

A client submission produces exactly one artifact: **the package** — a zip file. Its consumer
is a **fresh Claude Code session with zero other context**. That session must build a real,
multi-page website that visibly matches the client's sketch **without asking a single
clarifying question**. This is the round-trip test (Stage 4 DoD, `docs/decisions.md`
2026-07-27), and it is v1's definition of done. Every design decision in this document is
subordinated to that consumer.

### 0.1 The three-artifact redundancy model

The package deliberately says everything three times, in three forms, with a stated
precedence order:

| Artifact | Form | Role |
|---|---|---|
| `site.json` | machine-readable JSON | **Structural and content truth.** Exact geometry, z-order, text, copy modes, links, asset refs, pen strokes. |
| `pages/*.png` | rendered images | **Spatial ground truth + the pen marks.** What the client actually saw: positions, sizes, overlap, reading order, and every handwritten stroke. A *sketch render*, not a design mock — see the carries/does-not-carry table below. |
| `brief.md` | narrative prose | **Intent and instructions.** The build prompt: role framing, walkthroughs, copy-to-write list, style directives, done criteria. Generated FROM `site.json` by a fully specified generator — it can never drift from it. |

**What the PNG does and does not carry (binding — every "check the PNG" instruction in
this spec and in `brief.md` must be consistent with this table):**

| The PNG DOES carry | The PNG does NOT carry |
|---|---|
| Block positions, sizes, overlap, spacing, reading order | Typography: font family, size, weight (it renders default sketch type) |
| Which blocks sit side by side | Text alignment inside a block (editor default, zero client intent) |
| Section band extents and any explicit background colors | Styling of nav bars, buttons, body text (sketch chrome) |
| Pen strokes, exactly as drawn (the only place they are readable) | Anything about other viewport widths — it is a fixed 1200px raster: no full-bleed vs capped answer, no breakpoints, no mobile |
| How an uploaded photo is framed in its slot | Final appearance of empty image slots (it shows a dashed placeholder box + description text — sketch chrome, never to be reproduced) |

**Precedence order (binding, printed inside `brief.md` itself):**

1. For **content and structure** (what text a block holds, what a button links to, which
   copy is real vs generate, which asset goes where): `site.json` wins — **including its
   `penRegions` (v2.5), which are drawn content and rank exactly as high as `blocks`.**
   A stroke listed in a region's `strokeIds` IS that region's content; `penStroke.role` and
   `targetBlockId` describe only the ink no region claimed (§2.9). This clause is spelled out
   here because the shipped brief prints it, and because without it a builder applying rule 1
   literally to a package whose every stroke reads `role: "annotation"` would conclude a
   pen-only page is empty and ship it blank.
2. For **spatial questions** (position, size, overlap, reading order) and for **reading
   the client's pen marks**: the page PNG wins. For everything in the PNG's
   does-NOT-carry column, the PNG carries no design intent at all — style comes from
   `siteSettings` and the builder's judgment, per the brief's Look & feel section.
3. `brief.md` never overrides either. It is derived output. If the brief appears to
   contradict the JSON or the PNG, the brief is wrong — a generator bug — and the builder
   follows 1 and 2.
4. **Legible handwritten pen annotations are client instructions — the newest thing the
   client did.** Where a legible annotation asks for a change to content or layout, the
   builder follows it over 1 and 2 and logs it in `BUILD_NOTES.md` under "Pen
   instructions followed". Where a mark is illegible or unclear, the builder builds what
   1 and 2 say and logs the unread mark (page + coordinates) under "Pen marks I could
   not read" so Cam can raise it with the client.

Rationale: JSON and PNG are generated from one in-memory state in one export pass, so
they agree on everything both express; the PNG additionally renders sketch affordances
(default typography, dashed empty-slot frames, editor nav styling) that carry no design
intent — which is why precedence #2 scopes the PNG to spatial facts and pen marks. The
rules above make every interpretation question answerable without asking a human.

## 1. Zip layout

```
blueprint_<business-slug>_<uuid8>.zip
├── site.json          ← machine truth (this spec §2)
├── brief.md           ← the build prompt (this spec §3)
├── pages/
│   ├── 01-home.png    ← one PNG per page: <NN>-<slug>.png, NN = 2-digit 1-based page order
│   ├── 02-menu.png
│   └── 03-contact.png
└── assets/
    ├── img_001.jpg    ← client-uploaded images: <asset-id>.<ext>, ext from MIME type
    └── img_002.png
```

Rules:

- **All four entries live at the zip root.** No wrapper folder — a builder that extracts and
  runs `ls` sees `site.json` and `brief.md` immediately.
- **Nothing else goes in the zip.** No README, no thumbnails, no `.blueprint` file. Exactly:
  `site.json`, `brief.md`, one `pages/<NN>-<slug>.png` per page, zero or more
  `assets/img_NNN.<ext>` files. Validators treat unexpected entries as a packaging error.
- Zip filename: `blueprint_<business-slug>_<uuid8>.zip` where `<business-slug>` is the
  slugified business name (§4.1) and `<uuid8>` is the first 8 hex chars of the submission
  UUID. Example: `blueprint_bluebird-bakery_3f2a9c1e.zip`. The filename is cosmetic — all
  identity data also lives inside `site.json` (submission block), per debate #2's binding
  "submission-UUID stamped into zip and notification alike".
- Paths inside `site.json` (`page.screenshot`, `asset.path`) are **zip-relative with forward
  slashes**, exactly as they appear above.
- `assets/` may be absent entirely if the design references no uploaded images. `pages/` is
  always present (≥1 page).
- **File conventions:** `site.json` and `brief.md` are UTF-8, no BOM, LF line endings.
  `site.json` is written by the **canonical serializer — exactly
  `JSON.stringify(data, null, 2)` plus a trailing LF** (v2.4; no hand formatting, no
  multi-value lines) with **stable key order — the §7.1 fixture's order is normative**
  (v2.3; see §2.1) — required for the deterministic-output claim in §4, for meaningful
  fixture diffs, and byte-tested by Appendix A test D. Zip entries are written in the
  order listed above:
  `site.json`, `brief.md`, `pages/` in page order, `assets/` in id order.

## 2. `site.json`

### 2.1 Top-level shape

```jsonc
{
  "schemaVersion": 1,          // always the integer 1 for this spec
  "submission": { ... },       // who sent it, when — §2.3
  "siteSettings": { ... },     // site-wide facts — §2.4
  "pages": [ ... ],            // ordered; pages[0] IS the homepage — §2.5
  "assets": [ ... ]            // manifest of every file in assets/ — §2.9
}
```

**Key order is normative, and §7.1 is the canon (v2.3 ruling).** Determinism is one of
this contract's design principles — two exports of the same design must be
byte-identical so packages are diffable across round-trip iterations — and a normative
key order is what makes that checkable. Where any §2 listing and the §7.1 fixture have
ever disagreed (historically: `z` before vs after `frame` on blocks), **the fixture
wins**: block keys are `id`, `type`, `z`, `frame`, then `fromTemplate` when present
(§2.6, v2.4 — §7.1 has no flagged block to pin it, so the §2.6 table order is blessed
as canon), then the per-type fields; every implementation and every Appendix A test
targets §7.1's order. The serialized FORM is likewise canonical: `site.json` is exactly
`JSON.stringify(data, null, 2)` + LF (v2.4; §1), byte-tested by Appendix A test D. V27
(WARN) checks order at package time — divergence is a producer bug, never
client-fixable.

Design choices worth naming:

- **`submission` is a top-level sibling of `siteSettings`, not nested inside it.** Site
  settings are facts about the *website* (they feed the brief's style section); submission
  metadata is facts about the *transaction* (who, when, which UUID). Keeping them separate
  means future tooling (inbox, dedupe, revision-tracking) reads `submission` without
  touching design data.
- **`pages[0]` is the homepage.** No `isHome` flag — array order is meaningful (it is the
  client's page order from the page strip) and position 0 carries the homepage role. The
  brief states this explicitly so the builder never wonders.
- **The nav graph has no dedicated field.** Link data lives on `button` and `navBar` blocks
  (the only things that can link); the graph is derivable by walking them. `brief.md`
  prints the derived nav map (§3), so the builder gets the graph in narrative form while
  the JSON keeps a single source of truth. (The master plan's `navLinks` sketch is
  superseded by this — links-on-blocks is lossless and simpler.)
- **Export names are the public contract, not the internal store ids.** The palette's
  internal ids are `section, heading, text, image, button, nav-bar`
  (`src/constants/blockTypes.ts`); the export discriminators are
  `section, heading, text, imageSlot, button, navBar`. The export generator maps
  `image → imageSlot` and `nav-bar → navBar` (§4.6). Internal ids may change; the export
  contract may not.

### 2.3 `submission` — field by field

| Field | Req | Type | Intent / default |
|---|---|---|---|
| `id` | ✔ | UUID v4 string | The submission's identity, minted at submit time. Stamped here AND in the zip filename AND in the notification email (debate #2 binding). Never reused; re-submitting the same design mints a new one. |
| `submittedAt` | ✔ | ISO 8601 datetime (UTC, `Z` suffix) | When Submit was pressed. |

### 2.9 `penStrokes[]` — field by field

Freehand pen layer (Stage 2 `feature-pen-layer.md`). Strokes serialize fully — the PNG bakes
them visually, the JSON preserves them structurally (future revision-sketch tooling reads
them; the v1 builder mostly consults the PNG).

**Read the scope note below the table before reading `role`.** Ink that a `penRegion` claims
is design content, and `role` is not a statement about it.

| Field | Req | Type | Intent |
|---|---|---|---|
| `id` | ✔ | `stk_` + 4–16 `[a-z0-9]` | Export identity, remapped at package time (§4.8 — ordinal `stk_0001`… site-wide in draw order). |
| `points` | ✔ | array of `[x, y]` pairs, ≥2 | Page coordinates, in draw order, after point-thinning (§4.5). Numbers rounded to 1 decimal to cap payload. |
| `color` | ✔ | hex | Stroke color as drawn. |
| `width` | ✔ | number > 0 | Stroke width in design px. |
| `role` | ✔ | `"annotation"` \| `"imageSketch"` | **Which kind of NOTE an UNCLAIMED mark is — see the scope note below; it says nothing about a stroke some `penRegion` claims.** **Computed at export** (§4.5, pure geometry — the 60% rule applies whether or not the slot holds an upload): `imageSketch` = the client drew *inside an image slot*. Its meaning branches on the slot: **empty slot** (`assetId: null`) → the drawing depicts what the desired image should contain; **filled slot** → the drawing is an *instruction about the uploaded image* (framing, crop, emphasis — "this part matters") and is NEVER a request to replace the upload. `annotation` = a note/arrow/circle about the layout ("make this bigger"). Stored explicitly so the consumer never re-derives geometry — but derived fresh each export, so it can't drift. |
| `targetBlockId` | ✔ | `blk_…` \| null | **Scoped exactly as `role` is — a guess about an UNCLAIMED mark, inert on a claimed one.** For `imageSketch`: the image slot sketched into (required, non-null). For `annotation`: a **guess** — the **non-`section`** block whose frame overlaps the stroke most, else the nearest non-`section` block within 200px (§4.5; sections are excluded — v2.4), else `null`. The brief phrases it as a guess ("the nearest block is X, but the mark may be about something else"), never as fact. |

**Scope — `role` and `targetBlockId` describe ink that NO `penRegion` claims.**

A stroke listed in some `penRegions[].strokeIds` on its page (§2.5) is not a note *about* the
design: it **is** design, and its region's `kind` says which piece. `role` answers "what kind of
NOTE is this mark?", and that question is only ever put to ink no region claimed. So
`role: "annotation"` on the strokes of a drawn pricing card is not a competing second opinion —
it is the resting value of a question never asked of that ink, and `targetBlockId`'s
nearest-block guess is inert for the same reason. Per stroke, in precedence order:

1. **Claimed** — some `penRegion` on the page lists the stroke in `strokeIds`. The stroke is that
   region's content: build the region (§4.9, [N14]). `role` and `targetBlockId` MUST NOT be read
   as demoting it to commentary, and a consumer that treats them that way is misreading this
   contract, not finding a contradiction in it.
2. **Unclaimed** — no region lists it. Read `role` and `targetBlockId` exactly as the table above
   describes, and narrate the mark as an annotation cluster ([N7]).

The partition is total and unambiguous by construction: V28 proves every `strokeIds` entry
resolves on its own page and that no stroke is claimed twice, so "claimed" is a property of each
stroke, not a judgement call.

**Why this is spelled out.** It can be got wrong in exactly one direction, and that direction
ships a blank page. Three independent zero-context builders, given a real package in which every
stroke carried `role: "annotation"` and `penRegions` described two drawn pricing cards, all
reported that a strict reading of `site.json` alone would have them build nothing where the
client had drawn the cards; the brief's prose is what talked them out of it. Prose forcefulness
is not a contract. This note is also not a new policy — v2.5 already scoped the annotation
*narration* this way ([N7]'s cluster pool is the strokes no region claimed, §4.5); it gives the
FIELD the scope its narration already had.

**Why `role` gains no third value.** "This stroke is a region's content" is already stated, once,
by `penRegion.strokeIds`; a `role: "content"` would be a second copy of that same fact on the
other side of the relation, and two copies of one fact drift unless one is DERIVED from the
other — which is the whole reason §0.1 can let the package say things three times at all.
It would also break consumers that exhaustively switch on a closed two-value enum, three
of them in this repo: the round-trip harness's scenario language
(`scripts/roundtrip/scenarios/scenario.schema.json`, whose `penCluster.role` mirrors this enum),
V22 (which exempts `imageSketch` clusters by naming the other value), and
`scripts/roundtrip/manifest-diff.mjs`. The enum stays closed; its **scope** is what was missing.

## 3. `brief.md` — the build prompt

### 3.1 Contract

`brief.md` is **generated 100% from `site.json`** by a pure function
(`generateBrief(siteJson): string`). No hand edits, no second data source — this is what
makes drift impossible. It is simultaneously: the top of the fresh Claude session's context,
the human-readable summary Cam skims, and the text payload of the notification email
(debate #2: the notification carries `brief.md` + gzipped `site.json`).

It must read as a **direct instruction to the builder**, not documentation about a format.

### 3.2 Template

Below is the normative template. `{{…}}` = value interpolation; `{{#each}}…{{/each}}` =
repetition; `{{#if}}` = conditional inclusion. Generation algorithms for the computed parts
(walkthrough ordering, position phrases, nav map, pen clusters) are in §4.

**v2.5 wording amendment (2026-07-29) — the builder-convergence pass.** One real exported
package was handed to THREE independent zero-context Claude sessions. Every change marked
`v2.5` below fixes a place where the brief made a builder hesitate, guess, or diverge from
the other two: a rule that produced a different result each time (the unreadable drawn-nav
labels), a rule that contradicted another rule (the set's "N-up row" vs `Your role`'s
x/w authority; the band's two accessibility treatments; the drawn-nav link target vs
definition-of-done item 1), a rule that overshot its own data (a "sentence" fallback for a
2-word box; `extraBottomPx` described as the measurable gap), a count that understated the
work (the copy-list heading; the inventory's drawn-region count), an instruction pointing
at a source that was empty (`The business` and `Look & feel` on a pen-only package), and a
decision the brief left to the builder that it should have made (`<html lang>` with no
legible copy; the card title's heading level; definition-of-done item 4 on unreadable ink).
The schema, the counted markers and every V-check are untouched: this pass is prose only,
and §7.2 moves only where amended boilerplate is quoted into it.

```markdown
## Definition of done

Your build is complete when ALL of these hold:

1. One real page per inventory row. **Page 1 renders at the site root (`index.html` /
   `/`) — its slug is for the page title and nav label only, never a URL.** Every other
   page renders at its slug (`<slug>.html` or `/<slug>`); all internal links point at
   these URLs.
2. Every block **and every drawn region** in every walkthrough exists on the built page —
   including each section band as a full-width background band — in the same
   top-to-bottom, side-by-side arrangement as its sketch PNG at desktop width. Rows stay
   rows. (Match arrangement and proportion, not pixel positions; you are building a real
   site, not an image.) Each page has exactly one `<h1>`.
3. All navigation works: every wired link goes to its target; the shared nav (if any)
   appears on every page; unlinked items are handled where their rule is given — the
   Navigation map for a button or nav item, the **Drawn nav** bullet in the walkthrough
   for a word the client drew.
4. Every WRITE THIS COPY item above has final written copy; every real-copy block shows
   the client's text verbatim — words and line breaks unchanged, typos included, no
   editorializing. (You may turn an email address, phone number, or street address
   inside client copy into a link or semantic element.) **Handwriting you could not read
   has no verbatim form** — where a piece of copy came from ink you could not read, the
   fallback in that region's bullet IS its final copy, and this item is satisfied for it
   once you have used that fallback and logged the region under "Pen marks I could not
   read".
5. Every asset the `Assets` section lists appears in its slot with its fit and an alt
   text you wrote from its description — a package that lists none satisfies this on its
   own; every SOURCE AN IMAGE slot has its placeholder file and is listed in
   BUILD_NOTES.md under "Images to replace".
6. The look honors the vibe, colors, and style notes; every legible pen instruction is
   followed and logged; unreadable marks are logged; everything you added beyond the
   sketch (footer, page furniture) is logged.
7. The site runs locally with a single obvious command (or by opening `index.html`) —
   state which in BUILD_NOTES.md.
8. Every drawn region is a real, styled element: a set of drawn regions is ONE reusable
   component instantiated once per member, drawn artwork is real artwork, drawn words
   are real text, drawn placeholder lines are real body copy, and an empty drawn box is
   a real media placeholder. A region whose handwriting you could not read is still
   BUILT — using the fallback its bullet gives you — and logged in BUILD_NOTES.md under
   "Pen marks I could not read". A page that has drawn regions and ships blank is not
   done.
```

### 3.3 Template rules (binding on the generator)

1. **Order is fixed** exactly as above: role → business → look & feel → responsive rules
   → inventory → nav map → walkthroughs → copy list → assets → definition of done. The
   builder reads top-to-bottom; instructions must precede data. "Your role" and
   "Responsive rules" are fixed boilerplate (they interpolate nothing but constants);
   everything else is generated per the [N1]–[N12] rules in §4.4.
2. **All-caps markers `WRITE THIS COPY` / `SOURCE AN IMAGE` / `BUILD THIS FROM INK`**
   are load-bearing: they make every action item grep-able. The validator counts them
   with **frame-tuple-anchored regexes** (v2.1, one match per logical line, `m` flag —
   the marker sits mid-bullet after the block-type and frame tuple, so a start-of-line
   anchor alone matches nothing):
   - `^\s*- \*\*(Heading|Text)\*\* [^(\n]*\((-?\d+(\.\d)?, ){3}-?\d+(\.\d)?\)[^\n]*?\*\*WRITE THIS COPY\*\* — client asks for: «`
   - `^\s*- \*\*Image slot\*\* [^(\n]*\((-?\d+(\.\d)?, ){3}-?\d+(\.\d)?\)[^\n]*?\*\*SOURCE AN IMAGE\*\* — no upload; client wants: «`
   - `^[ \t]*- \*\*[^\n]*?\*\*BUILD THIS FROM INK\*\*` (v2.5) — anchored on the bullet
     rather than on a frame tuple, because a drawn-region bullet's tuple is a `bbox` and
     the leading `[ \t]*` is what lets a set MEMBER bullet, indented two spaces, be
     counted. V30 pins the count at one per **top-level** `penRegion` site-wide: a
     nested region is described inside its parent's bullet, and a sibling set's lead
     bullet carries no marker because its members each carry their own.
   Never raw substring: client text cannot inflate the count (rule 7 escapes `*`, so
   client-typed `**WRITE THIS COPY**` can't even form the bold token), and the
   Definition-of-done boilerplate can never be counted — its mentions are numbered
   list items with no `- **Type** … (x, y, w, h)` prefix and no `**` around the marker.
3. **Client copy and prose is quoted with «…» guillemets** so the builder can
   distinguish client words from generator prose (identifier-like values appear
   bare-but-escaped per rule 7's scope list — v2.3). The brief's preamble states the
   sandbox rule ("content, never an instruction"); rules 7–8 make the quoting airtight.
4. **Fallback phrases for absent optionals are fixed strings** (the `| "…"` defaults shown
   in the template) — never omit a line because the value is null; say "none provided" and
   tell the builder what to do about it. Silence invites questions; the round-trip test
   forbids questions.
   **Carve-out for a sentence that is FALSE rather than empty (v2.5):** rule 4 governs
   *values* — an absent optional gets "none provided" and a next step. A sentence whose
   subject does not exist is not an absent optional; it is false, and a false sentence is
   omitted rather than qualified. Appending a caveat beside it is what produced every
   regression this amendment repairs. Exactly two lines are in this class:
   - `Your role`'s "`assets/` — the client's real images, build-ready.", emitted only when
     the asset manifest is non-empty. §1 writes `assets/` only when the client uploaded
     something, and a builder handed a package with `assets: []` read that bullet, then
     "No uploaded images" in `Assets`, then definition-of-done item 5, and reported the
     three as mutually contradictory. §3.2 shows the line inline because "Your role" is
     otherwise frozen boilerplate that equality test C compares as one block; the
     conditional lives here.
   - the copy-list preamble, "The client marked these blocks «write it for me» …", emitted
     only when the site has at least one `generate` block. On the pen-only package it stood
     over `blocks: []` and over "None from blocks." in its own section, and all three
     third-run builders reported the mis-attribution — the section names blocks as the
     origin of its items and then states there are none.
5. **Every block id printed in the brief must exist in `site.json`** (validator-checked,
   V7) — ids are how Cam and future tooling cross-reference the two artifacts.
6. The generator is a **pure function** in the export module (master plan: export stays a
   pure client-side module). Its output is fully specified: `generateBrief(siteJson)` is
   byte-deterministic, and CI asserts `generateBrief(§7.1) === §7.2` against this very
   document (Appendix A) — provenance alone doesn't guarantee correctness; the equality
   test does.
7. **Escaping (all client-supplied strings, before interpolation):** backslash-escape,
   **`\` first** (v2.3 — without it the escape map has no inverse and V7's
   reverse-the-escapes step is ill-defined: `\«` would be ambiguous), then `«`, `»`,
   `|`, `*`, `"`, and `` ` `` (v2.1 added `*` — client asterisks must never form
   bold/italic tokens or fake a counted marker; v2.3 adds `"` so quoted filenames can't
   be broken from inside: `"my \"best\" photo\|final.jpeg"`). Prefix a leading `#`,
   `-`, or `>` with `\`; a leading ordered-list marker (digits then `.`) escapes the
   **period** — `1\. Order now` — because a backslash before a digit is a literal
   backslash in CommonMark and escapes nothing (v2.3).
   **Scope of quoting (v2.3 — replaces the earlier "never appears outside «…»"
   overclaim, which §7.2 itself legitimately violates six ways):** every client string
   is *escaped* wherever it appears; strings that are copy or free prose additionally
   appear inside `«…»`. A fixed set of identifier-like values appears bare-but-escaped:
   `businessName` (the H1 and the Name line), `tagline`, `about`, page `name`s (page
   headers, inventory, nav map, copy list, assets usage), `lengthHint` (both Length
   renderings), nav-item labels inside the shared-nav parenthetical, and
   `originalFilename` (inside `"…"`). V7's «…» cross-check applies to quoted
   occurrences only. Applies to: businessName, tagline, about, styleNotes, page names,
   block text, labels, descriptions, generateDescriptions, lengthHints,
   originalFilename.
8. **Newlines in client text:** inside `«…»`, CR/LF render as the `↵` glyph so the quote
   stays on one line; any multi-line `real` text block is ADDITIONALLY rendered beneath
   its bullet as an indented fenced verbatim sub-block, preserving line structure. The
   builder takes line breaks from the fenced block (or `site.json`), never from `↵`.
9. **No invented data.** The generator never emits information without a defining rule:
   no color-name guesses (bare hex only), no URL prettifying beyond [N9]'s host rule, no
   unit conversions beyond [N11]. If a rendering isn't defined in §3.2/§4.4, it doesn't
   appear in the brief.
10. **Line discipline (v2.1):** the generator emits **unwrapped logical lines** — exactly
    one physical line per paragraph, bullet, header, table row, or HTML comment; no hard
    wrapping. (Markdown renders identically either way, hard-wrapping risks splitting
    load-bearing markers across lines, and no single wrap width can satisfy all content —
    the v2 example was measurably unsatisfiable.) Verbatim fenced sub-blocks (rule 8)
    keep their internal newlines. §3.2's template is *displayed* wrapped for readability;
    "verbatim" in [N6] means the character sequence under whitespace normalization — the
    emitted form is always the single logical line. Appendix A's test B targets this
    unwrapped form byte-exactly.

## 4. Generation rules

How the app derives every computed value. All rules are deterministic — same design state,
same output (modulo timestamps/UUID minted at submit).

### 4.1 Slugs

`slugify(name)`:

1. Unicode-normalize (NFKD), strip diacritics, lowercase.
2. Replace every run of non-`[a-z0-9]` with a single `-`; trim leading/trailing `-`.
3. If empty (name was all symbols/emoji): use `page-N` (N = 1-based page position).
4. Truncate to **36** chars (at a `-` boundary where possible) — reserving room so a
   uniqueness suffix can never push past the schema's 40-char cap.
5. **Reserved names:** if the result is one of `index`, `assets`, `pages`, `site`,
   `brief`, `static`, `public`, append `-page`.
6. **Uniqueness:** on collision, append `-2`, `-3`, … in page order (first occurrence
   keeps the bare slug).

Applied to page names (→ `page.slug`) and the business name (→ zip filename slug; steps
5–6 don't apply to the business slug, and if the business name slugifies to empty the
business slug is `business` — v2.1). Slugs are computed **fresh at every export** from
current names — they are not stored in the design state, so renames can't leave stale
slugs. Note `pages[0]`'s slug is never a URL (§2.5 routing rule).

### 4.2 Page height

**One shared height function (v2.2 ruling):** the editor canvas and the export call the
same function — there are not two height computations to drift apart.

`bottom = max(all block bottoms (frame.y + frame.h), all stroke point-y)` on the page;
`height = clamp(1600, ceil((bottom + 160) / 8) * 8, 8000)`.

The +160 gives visual breathing room at the page foot; rounding keeps it on the grid;
the 1600 floor means a near-empty page still looks like a page (and matches what the
editor shows); the 8000 cap keeps a runaway canvas from producing an absurd PNG.
Because the editor uses this exact function, §4.3's "the page exactly as the editor
shows it" is literally true — same pixels, same height.

**Client-added room (v2.5):** a page may carry an optional `extraBottomPx` — empty
space the client asked for below their content with the editor's "Add space" control.
It is ADDED to the value above and the result re-clamped:

`height = clamp(1600, contentHeight + extraBottomPx, 8000)`, where `contentHeight` is
the formula above and `extraBottomPx` is 0 when absent.

Two properties of that placement are binding rather than incidental:

- **Purely additive**, so `height` is never below `contentHeight`. The editor's
  "Trim" control can therefore only ever give back space the client asked for — it is
  geometrically incapable of cropping a block or a stroke out of the deliverable,
  which matters because §4.3's render window clips at the page edge.
- **Added after the 1600 floor**, not before it, so one click of "Add space" grows
  the page by exactly that band even on a near-empty page (before the floor, the
  first several clicks would change nothing at all).

Absent, `height` is exactly what it was before the field existed.

### 4.3 PNG render contract

- **Dimensions: exactly `1200 × page.height`** design px at 1:1 scale (no devicePixelRatio
  multiplication — deterministic size beats retina crispness, and keeps the zip inside the
  email-forward size budget; ruling reaffirmed post-dry-run — revisit only if real pen
  handwriting proves illegible at 1×, and then as a spec revision, not an ad-hoc toggle).
- The render window starts at page coordinate y=0: any content at negative y **is clipped
  out of the PNG** (V18 warns on substantially off-page frames for exactly this reason —
  clipped content silently escapes the "PNG shows what the client saw" promise). Likewise
  the window ends at x=1200: content extending past the right page edge **is clipped at
  x=1200** (V25 WARN; [N13] marks such blocks in the brief; `site.json` keeps the true
  geometry — v2.1).
- Content: the page exactly as the editor shows it at 100% zoom with **all editor chrome
  removed** — no selection outlines, handles, grid dots, hover states, or cursors. White
  page background beneath the blocks. "Exactly as the editor shows it" is literal
  (v2.2): the editor and the export share one height function (§4.2) and the strokes
  are the committed strokes (§4.5), so canvas and PNG are the same pixels.
- **Pen layer baked in**, above all blocks, exactly as committed in the editor (the
  committed strokes are the only strokes that exist — §4.5 point thinning).
- Empty image slots render their dashed placeholder frame + description text (as in the
  editor) so the PNG shows the builder what the client saw.
- Renderer: snapdom, falling back to html-to-image behind the single export interface
  (debate #1 verdict). Each rendered PNG passes **sanity validation** — decodes, exact
  expected dimensions, non-blank pixel variance — with one retry, then engine fallback,
  before packaging proceeds (debate #1 binding mitigation; enforced again in §5).
  The non-blank check's ink floor is derived against a 1600px-tall page and scaled by
  `1600 / page.height` (never above 1), which makes it an absolute expectation about ink
  PIXELS rather than a ratio that quietly tightens as a page grows. It applies to every
  page carrying blocks, and to a **pen-only** page whose strokes predict several times
  the floor's worth of ink — never to a page whose one small mark could not clear the
  floor even when rendered perfectly, because there the floor cannot tell a failed
  capture from a sparse drawing.
- File: `pages/<NN>-<slug>.png`, `NN` = zero-padded 2-digit 1-based page order. The path
  is also written into `page.screenshot` — the JSON reference is authoritative; the naming
  convention is for humans browsing the zip.
- PNG compression: **lossless optimization only on any page containing pen strokes** —
  palette-reduction/lossy steps in the size ladder (debate #2) are permitted solely on
  stroke-free pages. This replaces the old subjective "legibility is the floor" wording
  with a checkable rule; V22 additionally warns on marks too sparse to be legible at all.

### 4.4 Brief narration algorithms (numbered — the template cites these as [N1]–[N14])

Every line of a generated brief must trace to the §3.2 template plus exactly one of these
rules. Nothing else may appear (template rule 9); CI enforces byte-equality against the
§7 fixture (Appendix A).

**Reference text (v2.3 — shared by [N5], [N7], and [N8]).** Wherever those rules print a
referenced block's "text/label", the string is: heading/text → `generateDescription`
when `copyMode` is `"generate"`, else `text` (V5 guarantees the description is non-empty
— a generate block must never be referenced as `«»`, which is what naive use of its
residual `text` produced); button → `label`; imageSlot → `description`; navBar → its
item labels joined with `, `; `section` blocks are never referenced. Where a reference
is truncated ([N5], [N7]): **truncate the raw string to 40 chars first, then apply
rule-7 escaping** — an escape pair is never cut in half and V7's escape reversal stays
well-defined.

**[N1] Section grouping.** Per page: take all `section` blocks sorted by `frame.y`. Every
other block belongs to the **first** section whose vertical range `[y, y+h)` contains the
block's center-y; blocks in no section band form the "Outside any section" group, and a
`navBar` whose center-y is above the first section is captioned "Nav bar". Groups are
emitted in order of their top edge. A page with **no** sections treats the first-section
boundary as +∞: a navBar still gets its "Nav bar" caption and everything else is
"Outside any section" (v2.3). A section band containing **no** blocks still emits its
header — DoD #2 requires the builder to build every band (v2.3).

**[N2] Rows and columns.** Within a group, partition blocks into **rows**: two blocks
share a row if their vertical ranges overlap by ≥ 50% of the shorter block's height
(transitive — union-find; a tall block therefore pulls a whole stack beside it into one
row, which is exactly the hero pattern). Emit rows in order of row top edge (min `y` of
members). Within a row, partition into **columns**: two blocks share a column if their
horizontal ranges overlap by ≥ 50% of the narrower block's width (transitive); order
columns by min `x`; order blocks within a column by `(y, then x)`. Narration: a row with
**one column** emits its blocks as plain bullets (covers single-block rows). A row with
**≥ 2 columns** emits the header `Row (side by side, left → right — K columns):`, then
one bullet per column — `Column k (left|middle|right{, stacked top → bottom when ≥2
blocks}):` — with the column's blocks as nested bullets (leftmost column is "left",
rightmost "right", any others "middle"). This is the brief's only ordering rule for
blocks — there is no flat `(y, x)` sort.

**[N3] Group headers.** Exact strings per the template: `Nav bar:`;
`Section band, full-width, y=<y>–<y+h> (background <#hex>) — render as a full-bleed
horizontal band; the blocks below sit inside it:`; the null-background variant with
`(no background set — choose one from the palette above, or leave it the page
background)`; `Outside any section:`. Ranges use an en dash [N11].

**[N4] Position phrases.** Deterministic vocabulary, always followed by the exact frame
numbers so no information is lost. Let `leftGap = x`, `rightGap = 1200 − (x + w)`:

- Width: `w ≥ 1120` → "spanning the full width"; `960 ≤ w < 1120` → "wide";
  `600 ≤ w < 960` → "about half the width"; `w < 600` → "narrow".
- Horizontal (omitted when full-width): `|leftGap − rightGap| ≤ 24` → "centered";
  `leftGap < rightGap` → "on the left"; else → "on the right".
- Example: frame (80, 160, 640, 96) → leftGap 80, rightGap 480 → "**Heading** about half
  the width, on the left (80, 160, 640, 96)". A 1040-wide block inset 80px each side is
  "wide, centered" — never "on the left".

**[N5] Overlap suffix.** If a block's frame intersects the frame of another non-`section`
block on the same page with lower `z`, append `(overlaps «X»)` where X is the lower
block's **reference text** (§4.4 preamble — truncate raw to 40, then escape; v2.3).
When a block overlaps **several** lower blocks, emit one suffix per overlapped block,
nearest paint-neighbour first (descending `z`) (v2.3). Sections are exempt (everything
sits on them by design).

**[N6] Per-type narration.** The template's branch texts are normative, verbatim —
including the asset-dimension lookup (`assetW`×`assetH` from the manifest) and the
alt-text-FROM-description instruction in both imageSlot branches. The empty-slot branch
requires `description` to exist — guaranteed by V14, so the branch has no null fallback.
The generate branch renders `generateDescription`; V5 guarantees presence, so
implementations may safely coalesce a null to `""` — the case is unreachable in a valid
package (v2.3). The **filled**-slot branch, whose `description` MAY be null (no
validator forbids it — V14 covers empty slots only, and an uploaded image without a
caption is a legitimate state): replace the entire `Client's description: «…» — write
alt text FROM this…` clause with the fixed sentence
`No description given — write alt text from what the image shows.`; the assets-section
usage entry likewise renders the bare fixed string `(no description)` in place of the
quoted description (v2.3 — fallback phrase adopted instead of a new V-rule, which would
nag clients about something the builder can infer from the image itself).

**[N7] Pen clusters.** Union-find over the strokes a page's `penRegion`s did not claim
(v2.5 — F5 clusters over UNCLAIMED ink, so a stroke published as a region to build is
not also narrated as a loose annotation): two strokes join if their
bboxes, each expanded by 40px, intersect — intersection is **inclusive**: touching
edges join (v2.3). Cluster role: `imageSketch` iff every member stroke is `imageSketch`
targeting the same slot, else `annotation`. Clusters are emitted in order of
cluster-bbox top edge. The imageSketch branch splits on the target slot's `assetId`
(empty vs filled — template text is normative). Annotation bboxes print as
`(x, y, w, h)` rounded to integers; the nearest-block guess names the target block's
type, its **reference text** (§4.4 preamble — truncate raw to 40, then escape), and
**the block's own frame** — never conflating it with the stroke bbox. For a
multi-stroke annotation cluster, the printed guess is that of the **first stroke in
draw order with a non-null `targetBlockId`**; if no member has one, the guess clause is
omitted per the template's `{{#if guess}}` (v2.3).

**[N8] Copy list.** Items numbered in walkthrough order (page order, then reading order
within the page). Header count pluralizes: `1 item`, otherwise `N items`. When
`lengthHint` is null, precompute the estimate before interpolation (no nested templates):
text blocks → `chars = (w / 8) × (h / 24)`, rendered as
`roughly ⌊chars/8⌋–⌊chars/5⌋ words`; heading blocks → `a short headline, a few words`.
Context line (v2.3 precision): candidates are blocks in the same group that are
**strictly non-overlapping vertically** — "above" means `candidate.y + candidate.h ≤
block.y`, "below" means `candidate.y ≥ block.y + block.h`; take the nearest by vertical
gap. A tall same-row neighbour is neither above nor below — this is exactly what makes
§7.1's answer (the heading, not the image slot beside it) correct. Names use the
reference text (§4.4 preamble). Render "sits under the heading «…», above the button
«…»"; omit a side that doesn't exist; when NEITHER side exists the line reads the fixed
string `nothing directly above or below it` — rule 4 forbids dropping the line (v2.3).

**[N9] Inventory "Links out".** Distinct internal page targets excluding self-links,
rendered as the page Name, in order of first appearance on the page; then distinct
external hosts (URL hostname, leading `www.` stripped). `—` if empty. Unlinked (`none`)
items never appear here — the Navigation map's conditional handles them.

**[N10] Resolved link-target rendering.** `kind: "page"` → `Name (`slug`)`;
`kind: "external"` → the full URL; `kind: "none"` → nav map: `button «label» — unlinked`
(buttons carry the `button ` prefix in the nav map; nav-bar items carry no prefix),
walkthrough bullet: `not linked yet — see Navigation map`. Self-links are listed in the
nav map like any other item. Iteration order: walk the page's blocks in `z` order; a
`navBar` contributes its items in their own order. Separators: nav-map entries join with
` · `; a walkthrough navBar's `items:` list and the unlinked-items list join with `, `
(unlinked entries render `Page name — button «label»`); the shared-nav label list joins
with `, `. A page with **no** buttons and no navBar renders its nav-map line as
`- **Name** → —`, reusing [N9]'s empty marker (v2.3).

**[N11] Number & text formatting.** File sizes: `~<round(bytes/1024)> KB`. Colors: bare
hex exactly as stored, comma-separated — never invented color names. Ranges: en dash
(`y=80–600`). Coordinates and dimensions: as stored (integers stay integers, one decimal
max). Dates: ISO 8601 as stored. Pluralization (v2.3): the inventory count line renders
`1 page` / `N pages` (a 1-page site must not read "1 pages"); the copy-list header
renders `1 item` / `N items` per [N8]. Asset usage entries join with `; ` — the entries
themselves contain commas (v2.3).

**[N12] Template-filler marker.** A block with `fromTemplate: true` whose narration
carries client-visible content gets the parenthetical marker (template text normative):
`(untouched template filler — treat as a request to write fitting content, do not ship
it verbatim)`. Sections are never narrated as bullets, so [N12] structurally cannot
fire for them — consistent with §2.6's v2.3 scope rule that the flag never appears on
`section` blocks in the first place.

**[N13] Right-overflow marker (v2.1).** If `frame.x + frame.w > 1200`, append to the
block's bullet — after the overlap suffix, before the colon — the marker
` (extends past the right page edge — clipped at x=1200 in the sketch PNG; site.json has
the true width)`. Inert on any block fully inside the page: the §7.1 fixture contains no
overflowing block, so this rule contributes zero bytes to §7.2 and test B is unaffected.

**[N14] Drawn-region narration (v2.5).** After the last narration group of a page and
before its `**Client's pen marks on this page**` block, emit one bullet per TOP-LEVEL
`penRegion`, in `site.json` order, under the header
`**What the client drew on this page** — build every one of these:`. Drawn content is
narrated after the blocks and ANNOUNCED before them (the lead paragraphs above), because
the builder needs "ink is content" before reading anything and needs the blocks
described before a region reads as page content among them. Rules:

- **Order** is `penRegions` order, which is already depth-first reading order (§2.5), so
  the bullets follow the page top to bottom. A sibling set is emitted where its FIRST
  member falls, as a lead bullet plus one two-space-indented member bullet per member in
  `setIndex` order; the remaining members are not emitted again at the top level.
- **Nesting.** A nested region is described inside its top-level ancestor's bullet, over
  ALL descendants rather than direct children only, so a grandchild is never lost. Its
  stroke ids are printed there too, which is what makes the 4× rebuild ladder reachable
  for every stroke the region owns.
- **Numbers must be measured.** A bullet may print a region's `bbox`, its `strokeIds`
  count, and — for `writing`/`navRow` — `text.words` and `text.glyphHeight`. It may NOT
  print a line count for handwriting: `text.lines` is `1` for every `writing` region
  because the producer counts rows only for a `textPlaceholder` stack, so a printed
  "2 lines" would be an unearned number. Ordering words is expressed as "topmost first"
  instead. A `textPlaceholder` DOES print its line count, taken as `strokeIds.length`:
  only a single-stroke squiggle is ever classified as a placeholder and the stack merger
  keeps one per line, so the two are equal by construction.
- **No `«…»`.** A region carries geometry and never text, so there is nothing an ink
  bullet could legitimately quote and V7's quote-provenance check can never fire on one.
- **`<h1>`.** The "so this is the `<h1>`" sentence is emitted on at most one region per
  page — the tallest top-level `writing` region whose `text.emphasis` is not `body` —
  and only when the page has no `heading` block. It is what makes definition-of-done
  item 2 satisfiable on a page the client drew instead of blocking out.
- **Inventory.** A page with ≥ 1 top-level region renders its inventory Blocks cell as
  `{{block count}} (+{{top-level region count}} drawn)`; a page with none renders the
  bare block count exactly as before.

Inert on a page with no regions: the §7.1 fixture publishes none, so this rule
contributes zero bytes to §7.2 and test B is unaffected.

### 4.5 Pen-stroke semantics and clustering

Role and clusters are computed at export time (never stored in editor state — derived
data stays derived). Point geometry, by contrast, is committed in the editor (v2.2 —
last bullet):

- **Per-stroke role (pure geometry — `assetId` plays no part):** compute the stroke's
  bounding box. If ≥ 60% of its area lies inside a single `imageSlot` frame on the same
  page → `role: "imageSketch"`, `targetBlockId` = that slot. Otherwise
  `role: "annotation"`; `targetBlockId` = the **non-`section`** block whose frame the
  stroke's bbox overlaps most (any overlap counts), else the non-`section` block with
  the nearest center within 200px, else `null`. **`section` blocks are excluded from
  annotation targeting entirely (v2.4)** — a full-width band always wins on overlap
  area, which would make every annotation "target" its background band and nothing
  else; §4.4's reference-text rule already declares sections unreferenceable, and §7.1's
  `stk_0002` demonstrably targets the button it circles, not the band behind it. The
  annotation target is a **guess** and is narrated as one (§2.9, [N7]). The *meaning* of an imageSketch branches on the slot's `assetId` at narration
  time (§2.9: empty = depicts the desired image; filled = instruction about the upload,
  never a replacement) — role assignment itself stays geometric so the rule is testable
  without content.
- **Clusters (brief only):** per [N7] — union-find with 40px-expanded bboxes; cluster
  role `imageSketch` iff every member targets the same slot; ordered by bbox top edge.
  **v2.5:** the pool is the strokes **no `penRegion` claimed** (§4.9), not every stroke on
  the page. Stated here as well as in [N7] because a reader implementing from this bullet
  alone would otherwise cluster over all of them and narrate drawn content twice — once as
  built structure and again as an annotation about it.
- **Point thinning (v2.2 — matches the shipped code):** strokes are thinned **once, at
  commit time in the editor**: a 0.75px minimum-distance pre-pass, then
  Ramer–Douglas–Peucker at ε = 0.5px, coordinates rounded to 1 decimal. The in-memory
  strokes ARE the thinned strokes — no un-thinned trail exists anywhere (it would sit in
  every autosave payload, and bare RDP on a 10k-sample stroke measured 18s; the pre-pass
  is what makes commit-time thinning affordable). The PNG is a DOM capture of those
  committed strokes, so **editor, PNG, and `site.json` all show the same geometry**. The
  export's own RDP pass at ε = 0.75px REMAINS as specified — it is measurably
  near-idempotent on committed strokes (240-sample scribble: 93→94 points, deviation
  0.741→0.743px) and exists so the export contract holds even if commit-time parameters
  drift. Fidelity, honestly stated: the committed stroke deviates from the raw pointer
  trail by ≈0.5px typically, 1.09px worst case over random hand-like input —
  imperceptible at 1:1, and identical in all three artifacts.

### 4.6 Asset naming and identity

- At export, assets referenced by at least one `imageSlot` are numbered `img_001`,
  `img_002`, … in **first-use order**: walk `pages[]` in order, blocks by `z`, and number
  each distinct asset at its first appearance. Deterministic and human-legible (the first
  image you meet in the site is `img_001`).
- File extension from MIME type: `image/jpeg → .jpg`, `image/png → .png`,
  `image/webp → .webp`. Path = `assets/<id>.<ext>`, recorded in `asset.path`.
- `originalFilename` preserves the client's filename verbatim (metadata only — never used
  as a path; it may contain anything).
- Images were already compressed at ingest (long edge ≤ 1600px — Stage 2
  `feature-image-upload.md`); export writes those bytes as-is. `width`/`height`/`bytes`
  describe the file in the zip, not the client's original.
- **Uploads not referenced by any slot are excluded** from the zip and the manifest (the
  client deleted the slot); the export must not leak them.
- Internal design-state asset ids (UUIDs or whatever the store uses) never appear in the
  export — `img_NNN` is the public identity, remapped fresh each export.

### 4.7 Discriminator mapping

Internal store block ids → export discriminators: `section → section`,
`heading → heading`, `text → text`, `image → imageSlot`, `button → button`,
`nav-bar → navBar`. The export module owns this mapping; changing an internal id is
invisible to consumers, changing an export discriminator is a breaking change (§6).

### 4.8 Identity remapping (internal ids → export ids)

Internal app ids are semantic and free-form (`rest-home-hero-title` — better E2E
selectors and debugging; ruled 2026-07-28). The export generator remaps **every**
page, block, nav-item, and pen-stroke id to the schema's patterns at package time,
exactly as §4.6 remaps assets to `img_NNN`:

1. **Scheme — ordinal in document order** (deterministic and diff-friendly; same design
   state → same export ids): pages → `pg_0001`, `pg_0002`, … in `pages[]` order; blocks
   → `blk_0001`, … numbered **site-wide** in document order (page order, then `z`); nav
   items → `nav_0001`, … site-wide (page order, navBar `z`, item order); strokes →
   `stk_0001`, … site-wide (page order, draw order). Zero-padded to 4 digits; the schema
   patterns (`{4,16}`) leave headroom if a count ever exceeds 9999 or a future version
   switches to hash-based ids.
2. **All references are rewritten consistently in the same pass**: `link.pageId`,
   `penStroke.targetBlockId`, and any future reference field.
3. **Internal ids never appear anywhere in the package** — not in `site.json`, not in
   `brief.md`. A leaked internal id is a packaging bug (V24, BLOCK).
4. **The remap table is NOT included in the package.** The builder doesn't need it and
   it would only invite confusion. (Logging it to the console at export time for
   debugging is fine.)

Stability note: export ids are stable within a package by construction and across
re-exports of an unchanged design; they shift when the client reorders or inserts
content — acceptable because each package is self-contained, and cross-package identity
is the submission UUID's job.

### 4.9 Ink region inference

How `page.penRegions` (§2.5) is derived: the algorithm that decides whether a run of
freehand ink is a **thing** (a drawn card, a drawn heading, a line of body text, a nav
row) or a **note about a thing**. Everything downstream of that answer — [N14]'s
`**BUILD THIS FROM INK**` bullets, [N7]'s clusters over *unclaimed* ink, V28–V31 —
depends on this section, so it is stated here completely enough to reimplement from.
§2.1 makes this document the contract: the shipped `src/canvas/ink/**` is **one**
implementation of these rules, and a re-derived consumer working from this section
alone must reach the same regions.

Five properties bind the whole pass:

1. **Pure geometry.** No ML, no network, no DOM, no `Date`, no `Math.random`, no
   mutation of the inputs. Same blocks + same strokes → byte-identical regions, which
   is what makes the feature unit-provable and what makes V27's determinism check
   hold over `penRegions` too. Stroke **colour** is the one non-geometric input, and
   it is read as an opaque family key (§4.9.2), never interpreted.
2. **It runs on the EXPORTED page.** Input is the page's already-remapped blocks
   (§4.8) and already-thinned, already-rounded strokes (§4.5 point thinning, §2.9
   one-decimal rounding). So the ids it hands back are the package's own
   `blk_NNNN`/`stk_NNNN`, and the geometry it measured is the geometry the builder
   receives. Inferring on internal state and translating afterwards would let the
   remap and the reading disagree — the same argument §4.5 makes for `targetBlockId`.
3. **Per page.** No region may cite a stroke, a block or a region on another page
   (V28 re-proves this).
4. **Coordinates are page pixels** (§0.2). The design width is fixed at **1200**
   (§4.3) and every ratio-of-the-page constant below multiplies it; the page's
   *height* is variable (§4.2), so no rule may clamp or normalize against it.
5. **Derived, never stored.** Recomputed from `blocks` + `penStrokes` at every export,
   exactly as `penStroke.role` is (§4.5), so a client who drags a block afterwards
   cannot leave a stale reading behind.

The pass has six stages, in order: **0** measure each stroke · **1** choose the
candidate set · **2** segment candidates into atoms · **3** classify each atom ·
**4** find sibling sets · **5** confidence, ordering and ids. §4.9.10 then states what
survives into the package.

#### 4.9.0 Stage 0 — the per-stroke measures

Every later threshold is a comparison against one of these. All are dimensionless or
in page pixels, and each guards its denominator: **a dead-straight stroke has a bbox
whose height (or width) is exactly 0**, so an unguarded ratio would be `w/0` or `0/0`,
and a `NaN` reaching a classifier is worse than a wrong answer — `NaN ≤ limit` is false
for *every* limit, so the ink would fall silently out of every branch instead of
landing in one.

| Measure | Definition |
|---|---|
| `bbox` | Axis-aligned box of the stroke's raw points. A mouse-drawn horizontal line has `h` **exactly 0**; a single-point stroke has `w = h = 0`. |
| `inkBbox` | `bbox` inflated by `width / 2` on all four sides, then clamped: `x ≥ 0`, right edge `≤ 1200`, `y ≥ 0`; **the bottom edge is not clamped** (the page height is variable). This is where perfect-freehand actually paints — the raw point box understates the mark — and it is the box a region publishes. |
| `pathLength` | Σ of consecutive point distances. |
| `closureGap` | Distance from the last point back to the first. Small ⇒ the shape closes. |
| `perimeterRatio` | `pathLength ÷ max(2·(bbox.w + bbox.h), 1)`. ≈1.0 for a rectangle, ≈0.79 for an inscribed ellipse. |
| `chordDev` | Max perpendicular distance from the first→last chord, ÷ `max(chord, 1)`. When the chord is 0 (a closed shape) the distance is taken from the first *point* instead, so a closed shape reads as an enormous deviation — which is the truth: it is nothing like a straight line. |
| `tiltDeg` | `atan2(\|Δy\|, \|Δx\|)` of the first→last chord, in degrees, folded into 0–90. |
| `hullFill` | Convex-hull area of the points ÷ `max(bbox.w · bbox.h, 1)`. Fewer than 3 points ⇒ hull area 0. Full for a blob, small for a wandering line. |
| `absTurn` | Σ\|change of direction\| along the **resampled** polyline, in radians (below). |
| `aspect` | `bbox.w ÷ max(bbox.h, 1)`. The `max` is the zero-extent guard, not a fudge. |

**Resampling and turning.** Walk the polyline at a fixed `RESAMPLE_STEP_PX` spacing,
keeping both endpoints. At sample *i*, direction is the angle of the chord from sample
*i −* `TURN_LEVER_SAMPLES` to sample *i +* `TURN_LEVER_SAMPLES`; `absTurn` is the sum of
`|wrapToPi(dirᵢ − dirᵢ₋₁)|` over consecutive samples in `[lever, n−1−lever]`, and is
**0** when that window is empty. Both halves matter:

- Resampling is what makes `absTurn` **scale-invariant** and immune to where the
  commit-time RDP pass (§4.5, ε = 0.5px) happened to keep vertices. Summed per raw
  vertex, the same shape drawn twice measures differently because the two pointer
  traces were thinned differently — the measure would be a property of the client's
  hand speed rather than of the shape.
- Summing the **change** between consecutive directions, rather than the angle between
  the two chords at each sample, is what stops the measure double-counting: overlapping
  windows inflate every result by roughly the lever length, so a closed convex outline
  would read as several revolutions. As specified, a traced square reads one
  revolution's worth (a little under — the first and last few samples have no lever
  arm), a straight line reads 0, and an arrow's two bends read 2–3 rad, which is what
  the artwork floor in §4.9.5 was chosen against.

Two helpers are used by later stages and are fixed here: **median** = the middle value,
or the mean of the middle two, and **0** over an empty set; **standard deviation** =
the *population* σ.

| Constant | Value | Why this value |
|---|---|---|
| `RESAMPLE_STEP_PX` | `12` | Roughly a third of the smallest glyph this module cares about, so a letter still contributes several samples. Also the smallest feature the module resolves at all — §4.9.5's real-letter floor is anchored to it. |
| `TURN_LEVER_SAMPLES` | `2` | A ±1 lever arm measures the noise between two adjacent samples; ±2 (a 24px arm at the step above) measures the shape. |

#### 4.9.1 The candidate set — which ink is eligible at all

Stage 1 asks which ink is **not design**. Both exclusions are positive reasons, not
heuristics, and both mirror rules §4.5 already states for `penStroke.role`.

1. **Draw order and ordinals.** Walk `page.penStrokes[]` in array order (= draw order,
   §2.5) and assign each stroke a 0-based **ordinal** *before* any exclusion. Ordinals
   are never renumbered, so the surviving sequence has gaps; an ordinal is the
   tie-break of last resort in every later ordering rule, which is why it must be
   stable against what the exclusions removed.
2. **Empty strokes are dropped** (`points.length === 0`). The schema requires ≥ 2
   points, so this is defence against a hand-edited file, not a real state.
3. **Image-slot sketch lock.** Drop a stroke when `containedRatio(bbox, slot.frame) ≥
   INK_IMAGE_SKETCH_AREA_RATIO` for **any** `imageSlot` block on the page. That is
   §4.5's 60% rule and the same predicate — a stroke that far inside a photo slot is a
   sketch *of the photo*; the export already narrates it that way ([N7], §2.9), and
   promoting it to a region would tell a builder to construct the client's doodle.
   The two copies of the constant are asserted equal by test, so they cannot drift.
4. **Block-overlap veto.** Drop a stroke when its `bbox` **meets** the `frame` of any
   **non-`section`** block on the page. A stroke touching a real block is a note
   *about* that block. One rule doing three jobs: it keeps "circle this button to
   emphasise it" an annotation, the case a wrong build would most obviously ruin; it
   is far **narrower** than a nearest-block radius, so a card drawn 100px below a real
   block is still a region (a radius rule would delete the client's drawn cards on any
   page that also has blocks); and it is what keeps the frozen §7.1 fixture
   byte-neutral — there the button and the annotation overlap by 3920 px², so the
   annotation leaves at this step.
5. **`section` blocks are exempt from the veto**, for exactly the reason §4.5 exempts
   them from the annotation guess: a full-width band always overlaps, so vetoing on
   one would veto the page.
6. **Both tests read the RAW `bbox`, never `inkBbox`** — the exclusions ask where the
   client's *points* are, not how wide the nib painted them.
7. **Performance bound.** If **more than `INK_MAX_STROKES` candidates survive**, the
   page publishes **no regions at all**. Note the bound is on candidates, after the
   exclusions above. This is deterministic, bounded, and identical to pre-v2.5
   behaviour, which is only safe because `penRegions` is deliberately *referential,
   not a total partition* (V28): nothing downstream may assume every stroke lands in a
   region, and every unclaimed stroke is still narrated by [N7].

**The veto's exact predicate, including the zero-extent-axis case.** `meets` is
**not** `intersectionArea > 0`:

```
meets(box, frame) =
  if box.w × box.h > 0 :  intersectionArea(box, frame) > 0
  else                 :  intervalsMeet(box.x, box.x + box.w, frame.x, frame.x + frame.w)
                      AND intervalsMeet(box.y, box.y + box.h, frame.y, frame.y + frame.h)

intervalsMeet(a0, a1, b0, b1) = a0 ≤ b1 AND b0 ≤ a1        // INCLUSIVE — touching counts
intersectionArea(a, b)        = overlap1D(x-axis) × overlap1D(y-axis)
overlap1D(aStart, aSize, bStart, bSize) =
  max(0, min(aStart + aSize, bStart + bSize) − max(aStart, bStart))
```

This is normative and was a **real shipped bug**, so the spec pins it. `intersectionArea`
multiplies two 1-D overlaps, so a dead-straight stroke — a constant-`clientY` (or
constant-`clientX`) mouse drag, whose bbox height or width is **exactly 0** — has one
factor of 0 and a product of 0, and reads as touching *nothing*. A rule laid straight
across a button slipped the veto and shipped as a buildable `rule` region. The question
"does the box meet the frame" is one **both** axes answer, so for a zero-area box it is
read per axis as an **inclusive** interval test: a rule lying exactly on a block's edge
is *on* the block, not beside it. The `w · h > 0` guard means this is the exact
`intersectionArea > 0` test for every non-degenerate box, so **no real drawn shape
changes answer** — only the zero-area case that was silently wrong, which is why §7.1
is unaffected. V28 re-proves the veto on the shipped geometry and **must apply this
identical predicate**.

`containedRatio` (used by clause 3 and again by §4.9.6) solves the same degeneracy the
same way — one axis at a time, then multiplied:

```
containedRatio(box, frame) =
  if box.w × box.h > 0 :  intersectionArea(box, frame) ÷ (box.w × box.h)
  else                 :  axisRatio(box.x, box.w, frame.x, frame.w)
                        × axisRatio(box.y, box.h, frame.y, frame.h)

axisRatio(start, size, fStart, fSize) =
  size > 0 ? overlap1D(start, size, fStart, fSize) ÷ size
           : (fStart ≤ start ≤ fStart + fSize ? 1 : 0)
```

Where both axes have length the product **is** the area ratio
(`(ovX·ovY)/(w·h) = (ovX/w)·(ovY/h)`), so this is the same rule read one axis at a
time — not a second one. Reading only the axis that has length is wrong and was also
shipped once: a straight line drawn 100px clear of a photo classified as a sketch *of*
that photo, because the photo's span on the ignored axis happened to contain it.

| Constant | Value | Why this value |
|---|---|---|
| `INK_IMAGE_SKETCH_AREA_RATIO` | `0.6` | Mirrors §4.5's `IMAGE_SKETCH_AREA_RATIO`. Held as a local copy rather than an import because the canvas layer must not depend on the export layer; a test asserts the two stay equal. |
| `INK_MAX_STROKES` | `400` | Far past any real sketch (the §7.1 fixture has 2) and keeps the enclosure search's worst case in milliseconds. Chosen so the degraded behaviour is *today's* behaviour rather than a partial reading. |

#### 4.9.2 Colour families — the only signal that separates overlapping ink

Candidates are partitioned by `penStroke.color` (exact string equality on the stored
`#rrggbb`) **before** any proximity rule runs, and enclosure detection and clustering
never cross a family.

Colour is the **only** signal that separates two ink objects whose boxes *overlap*,
which is precisely where every proximity constant is powerless — the gap is zero, so no
distance threshold can tell a red box from the blue writing drawn across it. It costs
nothing: `color` is already a required, already-serialized field (§2.9), so no new state
is introduced to get it. A region publishes the family it was segmented in as its
`color`.

The rule is crossed in exactly one place, on purpose: **containment claiming**
(§4.9.6) is cross-family, because a red box legitimately holds blue writing and a
client who switched pens mid-sketch has not changed what is inside what.

#### 4.9.3 Segmentation — candidates in, atoms out

An **atom** is one segmented run of ink: a scope, a colour family, a member set in draw
order, and two boxes (`bbox` = union of the members' raw boxes, used for measurement;
`frame` = union of their `inkBbox`es, the box a builder is handed). Atoms **partition**
the candidates — every candidate ends up in exactly one — and an atom's key is
`atom_<lowest member ordinal>`, unique by that partition.

Four passes, each of which exists because the one before it cannot do its job:

- **A. Colour** (§4.9.2) — the only separator that survives overlap.
- **B. Enclosures** (§4.9.4) — found next, because a container changes what "near"
  means for everything inside it.
- **C. Containment** (§4.9.6) — gives every remaining mark a **scope**, and two scopes
  never compare. This is what makes two pricing cards independent no matter how narrow
  the gutter between them.
- **D. Proximity** — union-find over the strokes left loose, **within one scope and one
  family only**.

Pass D's join test is on the **true** box gap (0 when the boxes overlap or touch), and
it is **anisotropic**: two strokes join iff `gapX ≤ CLUSTER_GAP_X_PX` **and**
`gapY ≤ CLUSTER_GAP_Y_PX`. The asymmetry is the whole point — letters and words must
join sideways readily, but a heading must **not** swallow the nav row drawn 40px
beneath it ("Cats-R-Us / Home Shop Contact" is exactly that page). Note this is a
**different** function from [N7]'s clustering, which expands *both* boxes by 40px and
so tolerates 80px of true gap in every direction; [N7] governs annotation narration and
is untouched by this section.

Atom members are sorted by ordinal; atoms are emitted sorted by ordinal. A cluster's
`color` is its family's.

| Constant | Value | Why this value |
|---|---|---|
| `CLUSTER_GAP_X_PX` | `40` | Words and letters run together horizontally; this is the width of a comfortable word space at sketch scale. |
| `CLUSTER_GAP_Y_PX` | `18` | Deliberately less than half of `CLUSTER_GAP_X_PX`: a line of writing must not vacuum up the line drawn under it. |

#### 4.9.4 Enclosure detection — is this ink a container?

An enclosure is the one primitive that changes the meaning of everything near it, so it
is found before proximity, not after. Within each colour family:

1. **Single-stroke first.** Every stroke that passes the single-stroke gates below
   becomes an enclosure on its own.
2. **Then fusion.** The strokes that did *not* become enclosures form the fusion pool.
   Repeatedly search that pool for the first connected subset of
   2..`ENCLOSURE_MAX_STROKES` strokes that measures like a box; on a hit, emit it as an
   enclosure, remove its members from the pool, and search again until none is found.
3. **A stroke that is already a box on its own is never a fusion candidate.** Without
   that rule two pricing cards 30px apart fuse into one enclosure spanning both: their
   union runs along 95% of every edge of its own box and their combined path is barely
   longer than that box's perimeter, so every fusion gate passes and the client's two
   cards become one. A box is a box; two boxes side by side are two boxes.
4. **Connectivity** for the fusion search: two strokes are neighbours iff
   `gapX ≤ ENCLOSURE_JOIN_GAP_PX` **and** `gapY ≤ ENCLOSURE_JOIN_GAP_PX`. People draw
   boxes in two pen-downs, and `ENCLOSURE_MAX_STROKES` covers "four sides, four
   strokes".
5. **Determinism of the search.** Seeds are tried in draw order, a subset only ever
   grows to member indices greater than its seed, reachable indices are visited in
   ascending order, each distinct subset is tested at most once, and the search stops
   after `ENCLOSURE_SUBSET_BUDGET` distinct subsets. The budget bounds the worst case
   **without** making the answer non-deterministic: the same input always examines the
   same subsets in the same order and always stops in the same place.

**Single-stroke gates** — all must hold:
`bbox.w ≥ ENCLOSURE_MIN_W_PX` · `bbox.h ≥ ENCLOSURE_MIN_H_PX` ·
`closureGap ≤ max(ENCLOSURE_CLOSE_GAP_PX, ENCLOSURE_CLOSE_GAP_RATIO × pathLength)` ·
`perimeterRatio ≤ ENCLOSURE_PERIMETER_MAX`.

**Fused gates** — over the subset's union `bbox` and its **summed** path length, with
`perimeterRatio = Σ pathLength ÷ max(2·(bbox.w + bbox.h), 1)`:

- cheap gates first: `bbox.w ≥ ENCLOSURE_MIN_W_PX` · `bbox.h ≥ ENCLOSURE_MIN_H_PX` ·
  `perimeterRatio ≤ ENCLOSURE_PERIMETER_MAX`;
- then a **perimeter floor**, `perimeterRatio ≥ ENCLOSURE_EDGE_COVERAGE`. This is not a
  new rule: ink cannot be within tolerance of 80% of *every* edge unless its path is
  roughly that fraction of the perimeter long, so stating it as a cheap gate prunes
  exactly the subsets coverage would have rejected, for none of the cost;
- then `edgeCoverage(bbox, member paths) ≥ ENCLOSURE_EDGE_COVERAGE`.

The cheap-first ordering is load-bearing rather than cosmetic: edge coverage costs 204
point-to-path sweeps and the search offers it thousands of subsets — measured on the
traced pricing-cards page, testing coverage before the size and perimeter gates made a
single call take over a second, while the size gates reject a row of glyphs in a few
arithmetic operations.

**Edge coverage** is the fraction of each of the four edges of the box that has ink near
it, **reported as the minimum of the four** — three good edges and one empty one is a
bracket, not a box. Each edge is sampled at `EDGE_COVERAGE_SAMPLES` evenly spaced
positions including both endpoints; a sample counts as covered when its distance to any
member stroke's **segments** is within `tol`. (Distance to segments, not to a densified
copy of the points: that is the exact value densification approximates, without
inventing a densification step whose size would quietly become another threshold.)

```
tol = min(EDGE_COVERAGE_MAX_TOL_PX,
          max(EDGE_COVERAGE_MIN_TOL_PX, EDGE_COVERAGE_DIAG_RATIO × hypot(bbox.w, bbox.h)))
```

The **cap** is measured, not guessed, and load-bearing. On the traced wave-and-cat
drawing the red wave's union box is 1080×91, so 6% of its diagonal is 65px — wide
enough that a sine curve wandering through the **middle** of the box counts as ink "on"
all four edges. It measured 0.84 coverage and fused into a panel: the page-wide
background wave would have been **built as a card**. The ratio exists to forgive a shaky
hand, not a shape that is nowhere near its own edge, and a hand does not get shakier
because the box is wider. Swept over the fixture corpus the wave measures 0.84 at 65px,
0.51 at 40px and 0.39 at 24px, while genuinely boxed ink — two L-shaped halves of a
200px box, and a 900px rounded rectangle split into two pen-downs — measures **1.00 at
every tolerance from 12px up**. The cap therefore only ever costs tolerance where
tolerance was doing harm, and it is set to the closure allowance because 24px is already
this module's statement of how far a hand may stray from where a box ought to be.

| Constant | Value | Why this value |
|---|---|---|
| `ENCLOSURE_MIN_W_PX` | `60` | Below this a shape is a letter or a tick, not a container worth building. |
| `ENCLOSURE_MIN_H_PX` | `40` | As above, on the short axis. |
| `ENCLOSURE_CLOSE_GAP_PX` | `24` | How far a drawn box may fail to meet itself. **The most tolerant** of the three closure tests considered, on purpose: the defect in the product owner's own drawing is "the pen strokes overshoot and leave gaps at the corners", and a `netTurn ≥ 5 rad` + corner-count gate fails on exactly that drawing — a rounded corner spreads ~90° over ~47px of arc, so a 12px resample step sees ~22° per vertex and counts **zero** corners. |
| `ENCLOSURE_CLOSE_GAP_RATIO` | `0.12` | The same allowance as a fraction of path length, so a big box gets a big allowance. |
| `ENCLOSURE_PERIMETER_MAX` | `1.6` | The honest rectangle/blob discriminator, and why a cat is never a panel: a rectangle measures ≈1.0, an inscribed ellipse ≈0.79, and the traced cat outline — ears, four legs, curled tail — measures 1.79. A wide measurable margin, not a coin flip. |
| `ENCLOSURE_JOIN_GAP_PX` | `32` | People draw boxes in two pen-downs; strokes closer than this may fuse. |
| `ENCLOSURE_MAX_STROKES` | `4` | Covers "four sides, four strokes". |
| `ENCLOSURE_EDGE_COVERAGE` | `0.8` | **Raised from 0.55 against the fixture corpus**, and it is the difference between a heading and a card. At 0.55 the traced word "Heading" — seven glyphs 56px tall, tops touching the top of its own box, V-bottoms touching the bottom, first and last strokes touching the sides — measured 0.66 and **fused into a panel**; so did a five-glyph display word, and so did two stacked body squiggles at 0.78. Genuinely boxed ink measures 1.00, and a hand-drawn box with a 60px gap in a 300px edge still measures 0.88. Nothing that is actually a box lives between 0.66 and 0.88; a row of letters does, so the bar belongs above it. |
| `ENCLOSURE_SUBSET_BUDGET` | `20000` | Ceiling on distinct subsets examined. Bounds a combinatorial worst case without making the answer input-dependent in any other way. |
| `EDGE_COVERAGE_SAMPLES` | `51` | 51 positions per edge — **odd**, so a midpoint is always tested. |
| `EDGE_COVERAGE_MIN_TOL_PX` | `12` | Floor of the tolerance: a steady hand is still a hand. |
| `EDGE_COVERAGE_DIAG_RATIO` | `0.06` | Tolerance scales with the box's diagonal… |
| `EDGE_COVERAGE_MAX_TOL_PX` | `24` (= `ENCLOSURE_CLOSE_GAP_PX`) | …but never past the closure allowance, for the measured reason above. |

#### 4.9.5 Classification — first match wins, in a fixed order

Each atom is classified independently, then two page-level passes revise the result.
The per-atom order is fixed and **carries meaning**:

```
panel → rule → textPlaceholder → writing → artwork → annotation
```

- **`rule` before `textPlaceholder`** so a dead-straight long line is a divider and a
  wobblier one is a line of body text.
- **`textPlaceholder` before `writing`** because the horizontal squiggle is the single
  most common mark a non-technical person makes, and every ordering that skipped it
  mis-built it three different ways.
- **`artwork` last, but still positively tested**, so an arrow never becomes art.
- **`annotation` is the residual and is still produced** — the ink returns to the pool
  §4.9.10 hands back to [N7], but it is never dropped. The worst case of this whole
  feature is "no change", never "wrong instruction".

`navRow` is not in the per-atom list: it is a **reclassification of `writing`** applied
by a page-level pass, because it needs a fact no single atom knows (§4.9.5.6).

**Gates and margins.** Every classifier is a **conjunction** of gates, each of the form
"value at least *limit*" or "value at most *limit*". A gate's margin is
`slack ÷ (|limit| or 1 when the limit is 0)` — relative, so 0.25 means the same thing
whether the limit is 0.05 radians of bow or 600 pixels of path. A classifier's margin is
the **minimum** across its gates (a conjunction is only as strong as its weakest term;
averaging would let three comfortable gates hide one that barely held), and the
classifier fails outright if any gate's margin is negative. **Only measured gates are
expressed as gates.** Discrete counts — how many strokes, how many lines, how many words
— are checked as plain preconditions and contribute no margin: a count of exactly the
minimum is not "barely" anything, it is exactly the rule, and an integer carries no
measurement noise to be near a boundary of.

**4.9.5.1 `panel`.** An atom that is an enclosure (§4.9.4) is `panel`, variant `card`,
and its margin is the enclosure margin the fusion or single-stroke test already
measured — read, not re-derived, so the confidence a panel reports is the confidence of
the test that made it.

**4.9.5.2 `rule`** — *solo atoms only* (exactly one member). Horizontal form, all gates:
`aspect(bbox) ≥ RULE_ASPECT_MIN` · `bbox.h ≤ RULE_MAX_THICKNESS_PX` ·
`chordDev ≤ RULE_CHORD_DEV_MAX` · `bbox.w ≥ RULE_MIN_LENGTH_PX` ·
`tiltDeg ≤ RULE_MAX_TILT_DEG`. Variant is **`divider`** when
`bbox.w ≥ RULE_FULL_WIDTH_RATIO × 1200` (= 660px), else **`underline`**. If the
horizontal form fails, the vertical form is tried with the axes swapped —
`bbox.h / max(bbox.w, 1) ≥ RULE_ASPECT_MIN` · `bbox.w ≤ RULE_MAX_THICKNESS_PX` ·
`chordDev ≤ RULE_CHORD_DEV_MAX` · `bbox.h ≥ RULE_MIN_LENGTH_PX` ·
`(90 − tiltDeg) ≤ RULE_MAX_TILT_DEG` — variant **`vertical`**. The tilt gate can never
bind on its own in the horizontal form (an aspect floor of 6 already caps the chord at
`atan(1/6) ≈ 9.5°`, inside the 12° allowance); it is kept because it **is** the binding
gate for the vertical form, and because a later loosening of the aspect floor must not
silently start admitting diagonals.

**4.9.5.3 `textPlaceholder`** — *solo atoms only*, the horizontal squiggle meaning "a
line of body text goes here". Gates: `aspect(bbox) ≥ PLACEHOLDER_ASPECT_MIN` ·
`bbox.h ≤ PLACEHOLDER_MAX_H_PX` · `chordDev ≤ PLACEHOLDER_CHORD_DEV_MAX` ·
`absTurn ≤ PLACEHOLDER_ABS_TURN_MAX`. `lines` starts at 1 and is revised by the stack
pass (§4.9.5.4). Looser than `rule` on every axis because it is a gesture, not a
construction: shorter, thicker, wobblier.

**4.9.5.4 The placeholder stack pass** (page-level, runs before emphasis and nav). A
**stack** of squiggles is one paragraph, not N dividers:

1. Group placeholder drafts into **columns**, keyed by scope, by walking them in order
   of `bbox.x` (ties by ordinal) and joining a draft to an existing column of the same
   scope whose **first** member's `bbox.x` is within `PLACEHOLDER_LEFT_TOL_PX`.
2. Within a column, sort by `bbox.y` and chain consecutive lines while the
   **bottom-to-bottom** gap is `≤ PLACEHOLDER_LINE_GAP_PX`; a larger gap ends the run.
3. A run of `≥ PLACEHOLDER_MIN_LINES` merges into **one** `textPlaceholder` draft over
   the union of its members, with `lines` = the run length and margin = the minimum of
   its members'. A shorter run is left as-is — a lone squiggle is a one-line
   placeholder, not nothing.

Grouping by **left edge first** and only then chaining down the page is what makes two
columns of body text two paragraphs: they interleave by `y`, so a purely vertical walk
would zip the left column's first line to the right column's first line. `MIN_LINES`
at 2 reads as "always stack what you can", but it is a knob rather than a no-op —
raising it to 3 would return a two-line stack as two single-line regions, which is what
a caller would want if two lines ever proved too little evidence for a paragraph.

**4.9.5.5 `writing`** — **two evidence routes, and an atom needs only one**, because
print and cursive share almost no measurable property. Without the cursive route every
single-stroke signed wordmark is lost; without the print route every neatly lettered
heading is.

- **Print route**, tried first, requires `members ≥ TEXT_PRINT_MIN_STROKES`. Gates:
  `aspect(atom.bbox) ≥ TEXT_MIN_ASPECT` ·
  `median(member widths) ÷ max(atom.bbox.w, 1) ≤ TEXT_GLYPH_WIDTH_RATIO` ·
  `max(member widths) ÷ max(atom.bbox.w, 1) ≤ TEXT_WIDEST_GLYPH_RATIO` ·
  `(max(member bottoms) − min(member bottoms)) ÷ max(atom.bbox.h, 1) ≤
  TEXT_BASELINE_SPREAD_MAX`.
- **Cursive route**, tried only when the print route did not match **and**
  `members ≤ TEXT_CURSIVE_MAX_STROKES`. Gates: `Σ absTurn ≥ TEXT_CURSIVE_ABS_TURN_RAD` ·
  `hullArea(all points) ÷ max(atom.bbox.w × atom.bbox.h, 1) ≤ TEXT_CURSIVE_HULL_FILL_MAX`
  · `aspect(atom.bbox) ≥ TEXT_CURSIVE_MIN_ASPECT`.

Consequence worth stating: an atom of **three or more** strokes that fails the print
route is never offered the cursive route, and falls through to `artwork`.

**Glyph height** (published as `text.glyphHeight`) is a **robust** median: take the
median of the members' `bbox.h`, keep the members whose height lies in
`[GLYPH_HEIGHT_LOW_RATIO × rough, GLYPH_HEIGHT_HIGH_RATIO × rough]`, and re-median over
those (falling back to the rough median if the band is empty). Capitals run tall and
descenders run long, and a plain median over a word like "Heading" is dragged by both;
re-medianing over the members that are plausibly the same size as each other is what
makes the answer the **x-height** rather than the average of the outliers.

**Words** (published as `text.words`) are the members sorted by `bbox.x`, cut wherever
the horizontal gap to the running word box is `≥ WORD_SPLIT_GAP_RATIO × max(glyphHeight,
1)`. Word segmentation is what makes nav detection possible at all.

**Emphasis and alignment** (page-level pass, over `writing` drafts only). Let `tallest`
be the largest glyph height among the page's writing drafts and `pageMedian` their
median. Then, in order:

1. `glyphHeight < HEADING_MIN_REAL_GLYPH_PX` → **`body`**;
2. `glyphHeight ≥ HEADING_MIN_GLYPH_PX` and `≥ tallest` → **`display`**;
3. `glyphHeight ≥ HEADING_MIN_GLYPH_PX` → **`heading`**;
4. `glyphHeight ≥ HEADING_RELATIVE_RATIO × max(pageMedian, 1)` → **`heading`**;
5. otherwise **`body`**.

Rules 1 and 4's floored denominator are two guards this branch must have, for one
measured failure: a hand-drawn dashed divider is five dead-flat dashes that cluster into
one writing run whose member heights are all **0**, so its median glyph height is 0.
Unfloored, `0 ≥ HEADING_RELATIVE_RATIO · 0` read as true and promoted a flat line to
the page's only `<h1>`. A run whose letters are shorter than one resample step carries
no letter shape, so it is body at most.

`align` is measured against the atom's **scope** — its containing panel's `frame`, or
the page box `{0, 0, 1200, 0}` at the top level: **`center`** when the atom's centre-x
is within `ALIGN_TOL_PX` of the scope's centre-x, else **`left`** when the distance to
the scope's left edge is `≤` the distance to its right edge, else **`right`**.

**4.9.5.6 `navRow`** — a page-level pass that **reclassifies `writing`**, run *after*
emphasis so it can see which word in the top band is the biggest: that one is the brand,
and the regular ones beside it are the navigation. A writing draft becomes `navRow` when
all of the following hold:

1. It is **in the top band**: its own `frame.y ≤ NAV_TOP_BAND_PX`, **or** its scope's
   `frame.y ≤ NAV_TOP_BAND_PX` (a nav row drawn inside a header box the client drew).
2. `NAV_MIN_WORDS ≤ words ≤ NAV_MAX_WORDS`.
3. Its `glyphHeight` is **strictly less** than the tallest glyph height among the
   banded writing drafts — the tallest is the wordmark, never the menu.
4. Gates over the gaps between consecutive word boxes:
   `medianGap ≥ NAV_MIN_GAP_RATIO × max(glyphHeight, 1)` ·
   `stdev(gaps) ≤ NAV_GAP_CV × max(medianGap, 1)` ·
   `median(word widths) ≤ NAV_MAX_WORD_WIDTH_RATIO × 1200` (= 264px).

Its margin becomes `min(navMargin, the writing margin)` and its variant is cleared to
`null` — a nav row is not display/heading/body. **Regularity, not just spacing**, is
what separates a nav row from a sentence: the gaps between nav items are near-equal and
a sentence's are not, and expressing that as a coefficient of variation makes it hold at
any size.

A nav row is **corroborated** — which forces `clear` confidence per §4.9.8 — when its
`frame.w ≥ NAV_MIN_SPAN_RATIO × 1200` (= 600px), **or** when a full-width `rule` draft
(one whose `bbox.w ≥ RULE_FULL_WIDTH_RATIO × 1200`) sits between 0 and
`NAV_RULE_ATTACH_PX` below the row's bottom edge. An independent corroborating signal
outranks a thin geometric margin: a nav row whose word gaps only just cleared their
threshold is still certain when a full-width rule sits right beneath it, because that
rule is evidence the gaps are not.

**4.9.5.7 `artwork`** — the residual, but positively tested. With
`members ≥ ARTWORK_MIN_STROKES`, gates: `hypot(bbox.w, bbox.h) ≥ ARTWORK_MIN_DIAG_PX` ·
`Σ pathLength ≥ ARTWORK_MIN_PATH_PX` · `Σ absTurn ≥ ARTWORK_MIN_ABS_TURN_RAD`. With one
or two strokes — less evidence — the gates are `Σ pathLength ≥ ARTWORK_MIN_PATH_PX` and
**either** `Σ absTurn ≥ ARTWORK_SOLO_ABS_TURN_RAD` (when the turn reaches it) **or**
`bbox.w ≥ ARTWORK_BAND_MIN_W_PX` (real width instead of real wander). Variant is
**`band`** when `bbox.w ≥ BAND_WIDTH_RATIO × 1200` (= 720px) **and**
`aspect(bbox) ≥ BAND_ASPECT_MIN` — a long, shallow drawing across the page is a
background wave, not a picture. An artwork of fewer than `ARTWORK_MIN_STROKES` strokes
is **forced `unsure`** (§4.9.8).

A cat outline (5–15 strokes, path length in the thousands, huge accumulated turn)
passes. An arrow — shaft plus two head strokes — measures ≈2–3 rad of turn and **fails**,
returning to the annotation pool. That turn floor is the entire defence against
promoting marginalia to artwork.

**4.9.5.8 `annotation`.** Anything that matched nothing. Margin is undefined, which
always reads as `unsure`.

#### 4.9.6 Containment — `parentRegionId` and the ancestor bound

1. **Claiming.** An atom's parent is the **smallest enclosure that holds enough of it**:
   among enclosures whose `bbox` area is **strictly greater** than the atom's and for
   which `containedRatio(atom.bbox, enclosure.bbox) ≥ CONTAINMENT_RATIO`, take the one
   with the smallest `bbox` area; ties go to the **lower ordinal** (the earlier draw).
2. **Strictly larger** is what makes cycles impossible: two boxes of equal area can
   never claim each other, so the parent graph is a forest by construction. V28
   re-proves it anyway.
3. **Claiming crosses colour families**, even though detection (§4.9.4) does not. A red
   box legitimately holds blue writing, and a client who switched pens mid-sketch has
   not changed what is inside what. This is the **one** place the family rule is
   crossed, and it is crossed on purpose.
4. **Enclosure chains are capped** at `MAX_CONTAINMENT_DEPTH` ancestors. An enclosure
   whose raw ancestor chain is longer is re-parented to the ancestor at index
   `chainLength − MAX_CONTAINMENT_DEPTH` (0-based, where index 0 is the immediate
   parent), which leaves it with exactly the cap. Two levels is a card inside a
   section; three is noise.
5. **Loose ink is parented to the enclosure that claims it, without a cap of its own** —
   handwriting inside the innermost card sits one level below that card. Three
   ancestors is therefore the producer's real ceiling, which is exactly the bound V28
   enforces; anything past it is a bug in the parent graph, not an enthusiastic client.
6. A region's `parentRegionId` is the published id of its parent atom's region, or
   `null` at the top level. A `panel` is the only kind that can be a parent, because
   only an enclosure can claim.

| Constant | Value | Why this value |
|---|---|---|
| `CONTAINMENT_RATIO` | `0.6` | An enclosure claims ink whose bbox is at least this contained in its own. |
| `MAX_CONTAINMENT_DEPTH` | `2` | Nesting past this collapses. Two levels is a card inside a section; three is noise. |

#### 4.9.7 Sibling sets — `setId` and `setIndex`

Two drawn boxes that match are **one component used twice**, not two boxes that happen
to look alike and get built by hand twice. This is the only construct in the whole pass
that turns a drawing into the *right* website rather than a faithful one.

1. **Scope.** Stage 4 runs over the page's **top-level `panel` regions only**
   (`parentRegionId === null`). Nested cards are their parent's business.
2. **Pairing.** Two panels are siblings when
   `|a.w − b.w| ≤ SIBLING_SIZE_TOL × max(a.w, b.w)` **and**
   `|a.h − b.h| ≤ SIBLING_SIZE_TOL × max(a.h, b.h)` **and** they share a line —
   `|centreY(a) − centreY(b)| ≤ SIBLING_ALIGN_TOL_PX` **or**
   `|centreX(a) − centreX(b)| ≤ SIBLING_ALIGN_TOL_PX`. Sibling pairs are transitively
   closed (union-find) into groups.
3. **Groups smaller than `SIBLING_MIN_MEMBERS` are discarded** — one instance is just a
   panel.
4. **The grid case.** A group forms a grid when **all** of: clustering by `centreY`
   yields ≥ 2 rows *and* clustering by `centreX` yields ≥ 2 columns (a cluster breaks
   wherever two adjacent centres are more than `SIBLING_ALIGN_TOL_PX` apart);
   `rows × cols` equals the group size; every row, sorted by `centreX`, has exactly
   `cols` members; each column's `centreX` values spread by `≤ SIBLING_ALIGN_TOL_PX`
   across rows; and the column gaps (measured on the top row) and row gaps (measured on
   the left column) each spread by `≤ SIBLING_GAP_TOL_PX`. The set is then the whole
   grid, ordered **row-major**. A grid of N identical cards is still ONE component used
   N times — a 2×2 features grid or a 2×3 pricing grid is the same claim as two cards
   side by side, just tiled; without this the single-axis reduction below would keep one
   row and the other cells would lose their `setId` and be built as unrelated panels.
5. **Otherwise, one row or one column.** The group is a **row** when its members'
   `centreY` values spread by `≤ SIBLING_ALIGN_TOL_PX`, else a **column**; order by
   `frame.x` (row) or `frame.y` (column), ties by ordinal. For **more than two**
   members, keep only the **longest run of consecutive members whose gaps all lie within
   `SIBLING_GAP_TOL_PX` of each other**; two members are kept whole. For three or more,
   size alone is a coincidence waiting to happen — a repeated component is *evenly*
   spaced. Stating the rule as "the longest regular run" rather than as a deviation over
   the whole set is what gives it an unambiguous answer when one member is out of step:
   the run wins, the outlier becomes a lone panel, and nothing depends on which member
   happened to be drawn first.
6. **If the reduction leaves fewer than `SIBLING_MIN_MEMBERS`, no set is emitted.**
7. **Numbering.** Each surviving set takes the next `set_` ordinal; its members'
   `setIndex` values are exactly `0..n−1` in the order fixed above — left→right for a
   row, top→bottom for a column, row-major for a grid. Sets are numbered in the order
   their first member appears in emission order (§4.9.9). Every other region carries
   `setId: null` and `setIndex: null`. V28 enforces the `0..n−1` density.

| Constant | Value | Why this value |
|---|---|---|
| `SIBLING_SIZE_TOL` | `0.15` | Hand-drawn boxes are never the same size to the pixel; 15% is the slop of a steady hand at card scale. |
| `SIBLING_ALIGN_TOL_PX` | `40` | Sharing a row or a column, and the cut distance when clustering centres into rows/columns. |
| `SIBLING_GAP_TOL_PX` | `40` | For three or more, the gaps must be regular too, or it is a coincidence. |
| `SIBLING_MIN_MEMBERS` | `2` | A repeated component is at least two instances. |

#### 4.9.8 Confidence — two levels, and what each obliges the brief to say

`confidence` is **`clear`** or **`unsure`** and nothing else. There is deliberately no
`low`: anything that would rank lower is not a region at all, it is an `annotation`.
Uncertainty always resolves **toward today's behaviour**, never toward a confident wrong
instruction.

Resolved in this order:

1. **Corroborated → `clear`.** An independent corroborating signal outranks a thin
   geometric margin (§4.9.5.6 is the only producer of this today).
2. **Forced unsure → `unsure`.** Set by a classifier that matched on reduced evidence —
   today, an `artwork` of fewer than `ARTWORK_MIN_STROKES` strokes.
3. **No margin → `unsure`.** A classification that matched nothing measurable.
4. Otherwise **`clear` iff `margin ≥ CONFIDENCE_MARGIN`**, where `margin` is the
   classifier's worst gate margin (§4.9.5).

**What each level obliges.** `clear` obliges nothing beyond the per-kind bullet: the
brief states the reading as a fact and tells the builder to build it. **`unsure`
obliges [N14] to append, to that region's bullet and whatever its kind, the fixed
sentence** `This reading is a geometric guess — if the PNG shows something different,
trust the PNG, build what you see, and log the difference in BUILD_NOTES.md.` (§3.2,
`confidence unsure, any kind`). That sentence is the whole contract of the level: an
`unsure` region is still built, still counted by V30, and still carries its
`**BUILD THIS FROM INK**` marker — what changes is that the PNG is named as the
tie-breaker, which is the precedence order the brief's role preamble already states.

| Constant | Value | Why this value |
|---|---|---|
| `CONFIDENCE_MARGIN` | `0.25` | A region that cleared its binding threshold by less than this **relative** margin is `unsure`. Relative, so one number governs the whole pass instead of a per-classifier fudge factor each. Counts never contribute (§4.9.5), which is what stops every two-line paragraph on every page reading `unsure` for no reason a client would recognise. |

#### 4.9.9 Emission order and ids

1. **Depth-first, in reading order.** Regions are emitted parent-first: a `panel`
   **immediately followed by everything inside it**, then the next top-level region.
   Within one parent (and at the top level), siblings are ordered by `frame.y`, then
   `frame.x`, then ordinal. This is the order §2.5 and [N14] cite, and V28 checks.
2. **Nothing is dropped by ordering.** A draft whose parent is somehow absent from the
   walk is appended in reading order after the depth-first emission rather than lost —
   losing the client's work is the one unacceptable outcome.
3. **Underline attachment is resolved last**, because it is the one internal field that
   names another region and therefore needs ids to exist. A `rule` of variant
   `underline` attaches to the **nearest** `writing`/`navRow` region whose bottom edge
   lies between 0 and `UNDERLINE_ATTACH_PX` above the rule's top edge and whose
   horizontal span strictly overlaps the rule's. This is producer-internal: v1 has no
   `penRegion.attachedToId` field, so the attachment informs the producer's own reading
   (and the editor overlay) and does not ship. Adding it later is an additive change
   (§6).
4. **Ids are minted in emission order**, from the export pass's own site-wide counter —
   the same counter that mints `pg_`/`blk_`/`nav_`/`stk_` (§4.8) — as `reg_` +
   `INK_ORDINAL_DIGITS`-padded ordinal. Because a parent is always emitted before its
   children, `parentRegionId` can only ever name an id that already exists, and V28's
   order check holds by construction.
5. **Set ids** are minted from the same counter as `set_` + padded ordinal, at the first
   region that belongs to each set, walking in emission order.
6. **Ordinals are dense across the `annotation` drop** (§4.9.10): a region that is not
   published never takes a number, so the published sequence has no holes for a reader
   to wonder about.
7. **Site-wide, not per page.** The inference itself is pure and per-page, so a
   standalone implementation may number from 1 on each page and re-mint on the way out;
   what the package must show is one dense site-wide sequence in page order, exactly as
   §4.8 requires of every other id.

| Constant | Value | Why this value |
|---|---|---|
| `INK_ORDINAL_DIGITS` | `4` | §4.8 — every ordinal id is zero-padded to four digits, as `blk_`/`stk_` already are. |
| `INK_REGION_ID_PREFIX` | `reg` | §2.2's `^reg_[a-z0-9]{4,16}$`. |
| `INK_SET_ID_PREFIX` | `set` | §2.2's `^set_[a-z0-9]{4,16}$`. |

#### 4.9.10 What is published, and the degenerate-input guarantees

**Publication.** Six of the seven kinds map 1:1 into `penRegion.kind`
(`panel`, `writing`, `navRow`, `rule`, `textPlaceholder`, `artwork`). **`annotation` is
dropped at the contract boundary** — the contract has no such kind, because that ink is
narrated by the [N7] cluster bullets exactly as it always was, and publishing it would
tell a builder to construct a doodle. Dropping happens *after* classification and
*before* id minting, which is what keeps the ordinals dense (§4.9.9 rule 6). Also:

- `bbox` is the atom's ink box (§4.9.0), rounded to **one decimal** — the same rule
  §2.9 rounds the points on, so a region's box never sits at coordinates its own strokes
  never visit.
- `variant` carries sub-**kinds** only (`card`, `mediaBox`, `divider`, `underline`,
  `vertical`, `band`) and is **omitted** when there is none. The `writing` emphasis words
  (`display`, `heading`, `body`) are an emphasis, not a shape, so they travel in
  `text.emphasis` where a builder knows to set type at that prominence.
- **A `panel` ALWAYS carries a variant, and it is the one thing that says whether the box
  is full or empty:** `card` when at least one published region names it as
  `parentRegionId`, `mediaBox` when none does. Both are the same `kind`, the same shape
  and the same geometry, and [N14] builds them as two different elements — a styled
  container in the site's own language, or an `<img>` placeholder the builder must source
  a picture for and log under "Images to replace". Before this rule the two were
  byte-identical in `site.json` and only the brief's prose separated them, so a consumer
  applying the JSON strictly built an empty box as a third empty card. V28 re-proves the
  agreement on the shipped data (a `card` with nothing inside it, or a `mediaBox` with
  something inside it, is a producer bug and BLOCKs).
  - **Decided over the PUBLISHED regions, after the `annotation` drop above.** The
    inference parents unclassifiable ink to the enclosure that holds it, so a box holding
    one doodle has a child in the inference's tree and nothing at all in the package.
    [N14]'s empty-box branch reads the published tree; deciding the variant anywhere else
    would let `site.json` and `brief.md` disagree about the same box.
  - It costs no schema change: `variant` is a free producer string by design (§6.2), and
    a consumer that does not recognise `mediaBox` falls back to `kind: "panel"` and builds
    a container — the same worst case as before, never a wrong instruction.
- `text` is present **only** for `writing` and `navRow`, and only when `words ≥ 1`;
  everything else carries `text: null`. Everything else has no words to count, and
  inventing a `text` block for it would tell a builder to look for lettering that is not
  there. `text.lines` falls back to **1**: the producer counts rows for a
  `textPlaceholder` stack, not for handwriting, whose letters it measures rather than
  its rows — which is exactly why [N14] forbids printing a line count for handwriting.
  `text.align` falls back to `left`, `text.emphasis` to `body` (so a `navRow` always
  reads `body`).
- `penRegions` is **omitted, never `[]`**, when nothing was published (§2.5) — an empty
  array would change the bytes of every package whose ink is all annotation, §7.1
  included.

**What publishing does to `penStroke.role`: nothing, and that is the point.** §4.5 computes
`role` for every stroke on the page, before this pass and independently of it, and what it
computes is which kind of NOTE a mark is. Publishing a region does not rewrite the strokes it
claims — it takes them **out of `role`'s scope** (§2.9's scope note), exactly as v2.5 already
took them out of [N7]'s cluster pool. So the reading order is fixed: a consumer resolves each
stroke against `penRegions` first, and consults `role` only for the ink no region claimed. A
package in which every stroke reads `role: "annotation"` while `penRegions` describes a drawn
card is not self-contradictory; it is the normal case, and the region wins.

**Degenerate inputs — the guarantees.** These are normative, not implementation notes:

1. **A zero-extent bbox never produces `NaN` and never silently escapes a rule.** Every
   ratio in §4.9.0 floors its denominator (`max(h, 1)`, `max(area, 1)`,
   `max(perimeter, 1)`, `max(chord, 1)`), and the two containment predicates answer the
   degenerate case **explicitly**, per axis (§4.9.1). A `NaN` reaching a classifier
   would be worse than a wrong answer: `NaN ≤ limit` is false for every limit, so the
   ink would fall out of every branch instead of landing in one.
2. **A dead-straight stroke over a block is vetoed** — this is the inclusive per-axis
   test of §4.9.1, and it is the reason that test exists.
3. **A single-point stroke is a legal candidate.** Its `bbox` is `w = h = 0`, its
   `pathLength`, `perimeterRatio`, `hullFill`, `absTurn` and `aspect` are all 0, its
   `chordDev` is 0, and its `inkBbox` is still a real box (the nib has width). It
   therefore fails every classifier and lands in `annotation` — which is a correct
   answer, not a hole.
4. **A run of flat marks is never promoted to a heading.** The real-letter floor and the
   floored page-median denominator (§4.9.5.5) both exist for this, against a measured
   failure: a hand-drawn dashed divider became a page's only `<h1>`.
5. **Ink that matches nothing is still emitted as a region by the inference** — it is
   never dropped *inside* the pass. At the contract boundary it becomes unclaimed ink,
   and unclaimed ink is narrated by [N7] (v2.5: clusters form over the strokes no region
   claimed). Between the two, **every stroke on the page reaches the builder in some
   form**, which is why V28 is deliberately referential rather than a total partition
   and why V30 pins one `**BUILD THIS FROM INK**` marker per top-level region.
6. **Past the candidate bound (§4.9.1 rule 7) a page publishes no regions at all**, and
   that is a documented silence rather than a failure: every stroke is then narrated by
   [N7], exactly as it was before v2.5.
7. **A page with no blocks is normal.** Nothing in this section requires a block to
   exist; the veto simply never fires, and V9 already rules that a page drawn entirely
   with the pen is a finished page.

## 6. Forward compatibility

1. **`schemaVersion` is a single integer, currently `1`.** It identifies the *contract*,
   not the app release.
2. **Additive changes do not bump it.** New optional fields, new enum values on
   producer-controlled enums (`vibe`, and from v2.5 `penRegion.variant` — a free
   producer string by design, so a new sub-kind never has to touch the schema), new
   WARN-level validations — all fine within version 1. Consumers MUST tolerate and
   ignore unknown fields everywhere (which is why the schema never sets
   `additionalProperties: false`) and MUST NOT fail on an unknown `vibe` or `variant`
   string: fall back to `penRegion.kind`, which IS a closed enum and does bump.
3. **Breaking changes bump to 2**: removing/renaming/re-typing any shipped field, changing
   a discriminator string, changing coordinate semantics or the zip layout, adding a new
   *required* field. Version 2 gets its own schema file; the repo keeps `site.v1.schema.json`
   forever so old packages remain validatable.
4. **Never re-purpose a field.** Deprecate by adding the replacement and continuing to
   write the old one until the next major bump.
5. **Known future extension points, reserved now** (do not improvise these ad hoc — each
   is a field the builder dry-run showed a builder inventing, and each lands as an
   optional field = no bump): a per-block `style` object and `block.alignment` (if the
   editor grows styling controls); `imageSlot.altText` (client-written alt, ending the
   write-it-FROM-description workaround); `imageSlot.focalPoint` (`{x, y}` normalized
   0–1, ending the object-position guess); `siteSettings.logoAssetId`;
   `siteSettings.fontPreference`; `siteSettings.colorRoles` (explicit
   primary/surface/accent, ending the first-color-is-primary convention);
   `navBar.brandAssetId` (wordmark/logo in the nav); a `submission.revisionOf` field
   (roadmap's revision-sketch feature); `penRegion.note` (a producer-written sentence
   about a region — reserved so an inference that learns to say something the geometry
   cannot has somewhere to say it, instead of being smuggled into `variant`).
6. **`site.json` and `.blueprint` are different contracts.** `.blueprint` is the internal
   design-state serialization (versioned independently, may change freely with a
   migration); `site.json` is the public export derived from it. Never let internal state
   leak into the export "because it's already there".
7. The brief's HTML comment header carries `schemaVersion` and `appVersion`, so even a
   stray `brief.md` separated from its zip is traceable.
